Big Idea 1 — Creative Development (CRD): Review Notes

Syllabus: AP Computer Science Principles — Course and Exam Description, Effective Fall 2020
Exam Weight: 10–13% of AP Exam
Topics: 1.1–1.4
AP Classroom: Topic Questions ~20 multiple-choice

Overview

Big Idea 1 introduces how computing innovations are created, starting with collaboration — how diverse perspectives, online tools, and interpersonal skills improve the development of computing innovations. It then defines what programs and code segments are and how they function, including inputs, outputs, and event-driven programming. Next, it covers the program development process: investigation, design, prototyping, testing, documentation, and acknowledging the work of others. Finally, it addresses identifying and correcting errors — logic, syntax, run-time, and overflow errors — and using test cases to check correctness. These ideas form the foundation of the course’s computational thinking practices and are especially important for the Create performance task, where you will collaborate, iterate, document, and test a program of your own.

In this big idea you will learn to:

  • Explain how computing innovations are improved through collaboration, explain how they are developed by groups of people, and demonstrate effective interpersonal skills during collaboration
  • Describe the purpose of a computing innovation and explain how a program or code segment functions
  • Identify the input(s) to a program and the output(s) it produces, including how events trigger event-driven programs
  • Develop a program using an iterative and incremental development process, and design a program and its user interface
  • Describe the purpose of a code segment or program by writing documentation, and acknowledge code segments used from other sources
  • Identify and correct errors in algorithms and programs, and identify inputs and expected outputs that can be used to check correctness
💡 Exam Tip

  • Learn the two Enduring Understandings cold: CRD-1 (incorporating multiple perspectives through collaboration improves computing innovations) and CRD-2 (developers create using an iterative design process that is user-focused, incorporates implementation/feedback cycles, and leaves room for experimentation and risk-taking). Most multiple-choice answers about “why collaborate” map to diverse perspectives help avoid bias or the innovation reflects the diversity of talents of its designers.

  • Know the four development phases (investigating and reflecting; designing; prototyping; testing) and that the process is iterative (revisits earlier phases) and incremental (breaks the problem into smaller pieces). Questions frequently describe an activity and ask which phase it belongs to — a survey is investigation, a storyboard is design, testing at extremes is testing.

  • Be able to classify the four error types (logic, syntax, run-time, overflow) from a scenario, and memorize the debugging techniques (test cases; hand tracing; visualizations; debuggers; adding extra output statements). AP CSP MCQs often present a buggy code segment and ask for the error type or the correct test case (inputs at or just beyond the extremes).

  • Distinguish input from output, and recognize event-driven programming: program statements are executed when triggered by an event (a key pressed, a mouse clicked, a program started) rather than through the sequential flow of control.

Topic 1.1 — Collaboration

Key Concepts

Learning Objective [CRD-1.A] — Explain how computing innovations are improved through collaboration.

协作（collaboration）如何改进计算创新（computing innovation）的开发。核心概念：计算创新以程序（program）为功能核心；可分为物理设备、非物理计算软件或非物理计算概念三类；有效协作能融合多元才能与视角、帮助避免偏见（bias）；与用户沟通咨询（user feedback）对开发至关重要。

  • [CRD-1.A.1]: A computing innovation includes a program as an integral part of its function.
  • [CRD-1.A.2]: A computing innovation can be physical (e.g., self-driving car), nonphysical computing software (e.g., picture editing software), or a nonphysical computing concept (e.g., e-commerce).
  • [CRD-1.A.3]: Effective collaboration produces a computing innovation that reflects the diversity of talents and perspectives of those who designed it.
  • [CRD-1.A.4]: Collaboration that includes diverse perspectives helps avoid bias in the development of computing innovations.
  • [CRD-1.A.5]: Consultation and communication with users are important aspects of the development of computing innovations.
  • [CRD-1.A.6]: Information gathered from potential users can be used to understand the purpose of a program from diverse perspectives and to develop a program that fully incorporates these perspectives.

Learning Objective [CRD-1.B] — Explain how computing innovations are developed by groups of people.

计算创新（computing innovation）如何由多人团队开发。核心概念：在线工具（online tools）支持共享与反馈，促进协作；结对编程（pair programming）是常见的协作模型，两人在同一工作台合作编写代码。

  • [CRD-1.B.1]: Online tools support collaboration by allowing programmers to share and provide feedback on ideas and documents.
  • [CRD-1.B.2]: Common models such as pair programming exist to facilitate collaboration.

Learning Objective [CRD-1.C] — Demonstrate effective interpersonal skills during collaboration.

在协作（collaboration）过程中展现有效的人际交往技能。核心概念：包括沟通（communication）、达成共识（consensus building）、解决冲突（conflict resolution）与协商谈判（negotiation）。

  • [CRD-1.C.1]: Effective collaborative teams practice interpersonal skills, including but not limited to: communication; consensus building; conflict resolution; negotiation.

Example — Collaboration Scenario

A team of four students is developing a mobile app that helps users plan meals. Each teammate brings a different talent — one designs the user interface, one writes the program, one tests it, and one interviews potential users. Because the team includes students with different dietary needs, ages, and skill levels, they catch early that the app should offer vegetarian filters and larger text. When two members disagree about the layout, they reach a consensus through discussion. The team uses an online document to share ideas and give feedback, and the two programmers use pair programming at the same workstation. The final app reflects the diverse perspectives of the whole team rather than any single member.

The three types of computing innovation (CRD-1.A.2):

Type Definition Example
Physical A physical device that includes a program as an integral part of its function Self-driving car
Nonphysical computing software Software that runs on a device Picture editing software
Nonphysical computing concept An idea or practice that depends on computing E-commerce

Topic 1.2 — Program Function and Purpose

Key Concepts

Learning Objective [CRD-2.A] — Describe the purpose of a computing innovation.

描述计算创新（computing innovation）的目的。核心概念：其目的是解决问题（solve problems）或通过创造性表达（creative expression）追求兴趣；理解创新目的能让开发者更好地开发该创新。

  • [CRD-2.A.1]: The purpose of computing innovations is to solve problems or to pursue interests through creative expression.
  • [CRD-2.A.2]: An understanding of the purpose of a computing innovation provides developers with an improved ability to develop that computing innovation.

Learning Objective [CRD-2.B] — Explain how a program or code segment functions.

解释程序（program）或代码段（code segment）如何运作。核心概念：程序是执行特定任务的一组语句集合，常称为软件（software）；代码段是程序的一部分；程序需适应多种输入与情境；行为（behavior）指程序执行时的表现，常通过用户交互来描述。

  • [CRD-2.B.1]: A program is a collection of program statements that performs a specific task when run by a computer. A program is often referred to as software.
  • [CRD-2.B.2]: A code segment is a collection of program statements that is part of a program.
  • [CRD-2.B.3]: A program needs to work for a variety of inputs and situations.
  • [CRD-2.B.4]: The behavior of a program is how a program functions during execution and is often described by how a user interacts with it.
  • [CRD-2.B.5]: A program can be described broadly by what it does, or in more detail by both what the program does and how the program statements accomplish this function.

Learning Objective [CRD-2.C] — Identify input(s) to a program.

识别程序的输入（input）。核心概念：输入是发送给计算机处理的数据，形式可为触觉、音频、视觉或文本；事件（event）与某一动作关联并提供输入数据；在事件驱动编程（event-driven programming）中，语句由事件触发执行，而非按顺序控制流执行。

  • [CRD-2.C.1]: Program inputs are data sent to a computer for processing by a program. Input can come in a variety of forms, such as tactile, audio, visual, or text.
  • [CRD-2.C.2]: An event is associated with an action and supplies input data to a program.
  • [CRD-2.C.3]: Events can be generated when a key is pressed, a mouse is clicked, a program is started, or any other defined action occurs that affects the flow of execution.
  • [CRD-2.C.4]: Inputs usually affect the output produced by a program.
  • [CRD-2.C.5]: In event-driven programming, program statements are executed when triggered rather than through the sequential flow of control.
  • [CRD-2.C.6]: Input can come from a user or other programs.

Learning Objective [CRD-2.D] — Identify output(s) produced by a program.

识别程序产生的输出（output）。核心概念：输出是程序发送到设备（如屏幕）的任何数据，形式可为触觉、音频、视觉或文本；输出通常基于程序的输入或先前的状态（prior state，如内部变量值）。

  • [CRD-2.D.1]: Program outputs are any data sent from a program to a device. Program output can come in a variety of forms, such as tactile, audio, visual, or text.
  • [CRD-2.D.2]: Program output is usually based on a program’s input or prior state (e.g., internal values).

Example — Pseudocode (Event-Driven Program)

// Program: Hydration Tracker (event-driven pseudocode)
// Purpose: record each glass of water a user drinks and display the daily total.

glassCount ← 0

// Event 1: the app starts — supplies input and sets up the display
onEvent("start", "start", function() {
    display("Today's glasses: " + glassCount)
})

// Event 2: the user clicks the "Add Glass" button — the click is an event
onEvent("addButton", "click", function() {
    glassCount ← glassCount + 1                          // process the input
    display("Today's glasses: " + glassCount)            // output to the screen
})

Notice that the statements are not executed in a simple top-to-bottom sequence: they run only when an event triggers them (CRD-2.C.5). The click is a tactile input (CRD-2.C.1) that supplies input data to the program, and the updated count displayed on screen is the output (CRD-2.D.1), which depends on the program’s prior state glassCount (CRD-2.D.2).

Topic 1.3 — Program Design and Development

Key Concepts

Learning Objective [CRD-2.E] — Develop a program using a development process.

使用开发过程（development process）开发程序。核心概念：开发过程可以是条理有序的，也可以是探索性的；常用阶段包括调查与反思、设计、原型制作、测试；迭代（iterative）指基于反馈、测试或反思不断修订并可能重访早期阶段；增量（incremental）指把问题拆分为小块，确保每块先可用再加入整体。

  • [CRD-2.E.1]: A development process can be ordered and intentional, or exploratory in nature.
  • [CRD-2.E.2]: There are multiple development processes. The following phases are commonly used when developing a program: investigating and reflecting; designing; prototyping; testing.
  • [CRD-2.E.3]: A development process that is iterative requires refinement and revision based on feedback, testing, or reflection throughout the process. This may require revisiting earlier phases of the process.
  • [CRD-2.E.4]: A development process that is incremental is one that breaks the problem into smaller pieces and makes sure each piece works before adding it to the whole.

Learning Objective [CRD-2.F] — Design a program and its user interface.

设计程序及其用户界面（user interface）。核心概念：设计以调查（investigation）确定需求（requirements）；调查方式包括问卷调查、用户测试、访谈与直接观察；规格说明（specification）定义程序需求；设计阶段包含头脑风暴、规划与故事板、模块化组织、界面布局图以及测试策略的制定。

  • [CRD-2.F.1]: The design of a program incorporates investigation to determine its requirements.
  • [CRD-2.F.2]: Investigation in a development process is useful for understanding and identifying the program constraints, as well as the concerns and interests of the people who will use the program.
  • [CRD-2.F.3]: Some ways investigation can be performed are as follows: collecting data through surveys; user testing; interviews; direct observations.
  • [CRD-2.F.4]: Program requirements describe how a program functions and may include a description of user interactions that a program must provide.
  • [CRD-2.F.5]: A program’s specification defines the requirements for the program.
  • [CRD-2.F.6]: In a development process, the design phase outlines how to accomplish a given program specification.
  • [CRD-2.F.7]: The design phase of a program may include: brainstorming; planning and storyboarding; organizing the program into modules and functional components; creation of diagrams that represent the layouts of the user interface; development of a testing strategy for the program.

Learning Objective [CRD-2.G] — Describe the purpose of a code segment or program by writing documentation.

通过编写文档（documentation）描述代码段或程序的目的。核心概念：程序文档是对代码段、事件、过程（procedure）或程序的功能及其开发过程的书面描述；注释（comments）是写给程序员阅读的文档形式，不影响程序运行；应在开发全程持续记录，便于独立或协作环境下开发与维护正确程序。

  • [CRD-2.G.1]: Program documentation is a written description of the function of a code segment, event, procedure, or program and how it was developed.
  • [CRD-2.G.2]: Comments are a form of program documentation written into the program to be read by people and do not affect how a program runs.
  • [CRD-2.G.3]: Programmers should document a program throughout its development.
  • [CRD-2.G.4]: Program documentation helps in developing and maintaining correct programs when working individually or in collaborative programming environments.
  • [CRD-2.G.5]: Not all programming environments support comments, so other methods of documentation may be required.

Learning Objective [CRD-2.H] — Acknowledge code segments used from other sources.

注明（acknowledge）来自其他来源的代码段。核心概念：必须注明协作开发或他人编写的代码段；致谢可写在程序文档中，并应包含来源或原作者姓名（origin / original author’s name）。

  • [CRD-2.H.1]: It is important to acknowledge any code segments that were developed collaboratively or by another source.
  • [CRD-2.H.2]: Acknowledgement of a code segment(s) written by someone else and used in a program can be in the program documentation. The acknowledgement should include the origin or original author’s name.

Example — Pseudocode with Documentation

// findLargest(nums)
// PURPOSE: returns the largest value in the list nums.
// DEVELOPED: written after brainstorming and storyboarding with the team;
//            revised in the testing phase when a bug was found.
PROCEDURE findLargest(nums)
    largest ← nums[1]
    FOR EACH item IN nums
        IF item > largest
            largest ← item
        END IF
    END FOR
    RETURN largest
END PROCEDURE

// Code below written by J. Alvarez (source: www.example.com/library),
// used with permission — acknowledged in the program documentation.

The comment at the top is a form of program documentation (CRD-2.G.1, CRD-2.G.2): it is written to be read by people and does not affect how the program runs. Programmers document throughout development (CRD-2.G.3), and the acknowledgement at the bottom includes the origin and original author’s name for a code segment taken from another source (CRD-2.H.2).

Quiz-Extension — Documenting Preconditions (Parameter Constraints)

Quiz 1 (Questions 29 and 31) checks that a program’s documentation should include the constraints — preconditions — on the values a procedure accepts. The framework’s documentation EKs (CRD-2.G.1–CRD-2.G.5) do not state this explicitly, so add the following extension.

Learning Objective [CRD-2.K] — Describe preconditions (input constraints) in program documentation.

在程序文档中描述前置条件（preconditions）。核心概念：前置条件是对输入或参数（parameter）值的约束，在代码段正确运行前必须满足；例如除数不能为 0、列表索引必须在 1 到列表长度范围内；记录前置条件可帮助其他程序员正确调用过程，并使程序更易开发与维护。

  • [CRD-2.K.1]: A precondition is a constraint on the input or parameter values that must hold before a code segment runs correctly; documenting it is part of program documentation (extends CRD-2.G.1).
  • [CRD-2.K.2]: Example — a procedure that divides two numbers must document that the denominator must not be 0 (x ≠ 0), because division by 0 is undefined (and causes a run-time error in most languages).
  • [CRD-2.K.3]: Example — a procedure that accesses a list element by index must document that the index must be in the range 1 to LENGTH(list); an index outside this range is invalid.
  • [CRD-2.K.4]: Documenting preconditions helps other programmers call the procedure correctly and makes the program easier to develop and maintain (CRD-2.G.4).

(b) A procedure divide(a, b) computes a / b. State the precondition that must be documented for b, and explain why it is necessary. [2]

📖 参考答案 | Reference Answer

Topic 1.4 — Identifying and Correcting Errors

Key Concepts

Learning Objective [CRD-2.I] — For errors in an algorithm or program: a. Identify the error. b. Correct the error.

针对算法（algorithm）或程序中的错误：a. 识别错误；b. 修正错误。核心概念：四种错误类型——逻辑错误（logic error，行为不正确）、语法错误（syntax error，违反语言规则）、运行时错误（run-time error，执行时发生）、溢出错误（overflow error，数值超出存储范围）；有效的查找与修正方法包括测试用例、手工追踪、可视化、调试器及增加额外输出语句。

  • [CRD-2.I.1]: A logic error is a mistake in the algorithm or program that causes it to behave incorrectly or unexpectedly.
  • [CRD-2.I.2]: A syntax error is a mistake in the program where the rules of the programming language are not followed.
  • [CRD-2.I.3]: A run-time error is a mistake in the program that occurs during the execution of a program. Programming languages define their own run-time errors.
  • [CRD-2.I.4]: An overflow error is an error that occurs when a computer attempts to handle a number that is outside of the defined range of values.
  • [CRD-2.I.5]: The following are effective ways to find and correct errors: test cases; hand tracing; visualizations; debuggers; adding extra output statement(s).

Learning Objective [CRD-2.J] — Identify inputs and corresponding expected outputs or behaviors that can be used to check the correctness of an algorithm or program.

识别可用于检验算法或程序正确性的输入及对应的预期输出或行为。核心概念：测试使用定义好的输入（defined inputs）确保程序产生预期结果，并据此修订程序；测试输入应展示输入数据极值处（最小值和最大值）及其边界外的不同预期结果；识别合适的测试输入需要程序需求（requirements）。

  • [CRD-2.J.1]: In the development process, testing uses defined inputs to ensure that an algorithm or program is producing the expected outcomes. Programmers use the results from testing to revise their algorithms or programs.
  • [CRD-2.J.2]: Defined inputs used to test a program should demonstrate the different expected outcomes that are at or just beyond the extremes (minimum and maximum) of input data.
  • [CRD-2.J.3]: Program requirements are needed to identify appropriate defined inputs for testing.
Error Type Definition (from the framework) When It Happens
Logic error A mistake in the algorithm or program that causes it to behave incorrectly or unexpectedly The program runs but produces wrong results
Syntax error A mistake in the program where the rules of the programming language are not followed The code cannot be translated/recognized correctly by the language
Run-time error A mistake in the program that occurs during the execution of a program While the program is executing
Overflow error An error that occurs when a computer attempts to handle a number that is outside of the defined range of values When a value exceeds the range a data type can store

Example — Pseudocode (Buggy Program)

// Buggy version: computes the average of three quiz scores.
INPUT score1
INPUT score2
INPUT score3
average ← (score1 + score2) / 3        // LOGIC ERROR: score3 is left out
OUTPUT average

The program runs without crashing, but the result is wrong whenever score3 differs from score1 or score2 — a logic error (CRD-2.I.1). To find and correct it, a programmer could hand trace the code, add an extra output statement to display intermediate values, or run test cases with known inputs, e.g., score1 = 90, score2 = 80, score3 = 100 (expected average 90) — the buggy version would output 56.67, revealing the mistake. The correction is average ← (score1 + score2 + score3) / 3.

Quiz-Extension Notes — Non-Terminating Loops, Test Sufficiency, and Commenting Out Code

Quiz 1 (the Progress Check) tested three additional points beyond the official EKs: loops that never terminate, why a single passing test case is not enough, and a sixth debugging strategy (commenting out lines of code).

Learning Objective [CRD-2.L] — Identify and correct errors that cause a loop to run forever (non-terminating / infinite loop).

识别并修正导致循环永不停止（非终止循环 / 死循环，infinite loop）的错误。核心概念：非终止循环因其终止条件永远不为真而永不结束；常见成因是循环体内未更新循环变量或终止条件所检查的变量；修正方法是在循环体内更新循环变量，使终止条件最终成立。

  • [CRD-2.L.1]: A non-terminating (infinite) loop is a loop that never stops executing because its terminating condition never becomes true.
  • [CRD-2.L.2]: A common cause is that the loop variable — or the variable the terminating condition checks — is never updated inside the loop body.
  • [CRD-2.L.3]: Quiz 1 tests this repeatedly: in a REPEAT UNTIL loop, if the counter tested by the condition is not updated inside the loop, the condition stays false forever and the loop never ends, so the program never reaches its output.
  • [CRD-2.L.4]: To correct the error, update the loop variable inside the loop body so that the terminating condition eventually becomes true.
✏️ Exercise 1.4.5 — Non-Terminating Loop (5 marks)

Consider the following pseudocode, which is intended to output the sum of the integers from 1 to 5.

sum ← 0
i ← 1
REPEAT UNTIL i > 5
    sum ← sum + i
END REPEAT
OUTPUT sum

(a) Identify the error in the code segment, and state whether the program ever produces its output. [2]

(b) Explain why this error causes the loop never to terminate. [1]

© Show the corrected loop body. [2]

📖 参考答案 | Reference Answer

(a) The loop variable i is never updated inside the loop body, so the condition i > 5 never becomes true; the loop repeats forever and the program never reaches the OUTPUT statement. [2]

(b) The terminating condition depends on i, and i never changes (it stays 1), so 1 > 5 is always false and the REPEAT UNTIL loop never stops. [1]

© The corrected loop body adds an update so that i increases toward 5:

REPEAT UNTIL i > 5
    sum ← sum + i
    i ← i + 1
END REPEAT

Now i grows each repetition until the condition becomes true and the loop ends. [2]

Learning Objective [CRD-2.M] — Explain why a single passing test case does not prove a program is correct.

解释为何单个通过的测试用例（test case）不能证明程序正确。核心概念：一个通过的用例只能确认程序对该特定输入产生预期结果；其他输入仍可能暴露错误，因此不能证明程序对所有输入都正确；通过测试提供的是证据（evidence）而非证明（proof），故需测试极值及边界处的输入。

  • [CRD-2.M.1]: A test case that produces the expected outcome confirms only that the program behaves correctly for that specific input.
  • [CRD-2.M.2]: One passing test case cannot prove that the program is correct for every possible input — other inputs can still expose errors.
  • [CRD-2.M.3]: This is why testing uses defined inputs at or just beyond the extremes of the input range (CRD-2.J.2): passing tests provide evidence, not proof, of correctness.
✏️ Exercise 1.4.6 — Why One Test Case Is Not Enough (4 marks)

A programmer tests a grading program with the single input 92; the program correctly outputs A. The programmer concludes that the program is fully correct.

(a) What does the single passing test case actually confirm? [2]

(b) Explain why the programmer’s conclusion is unjustified. [2]

📖 参考答案 | Reference Answer

(a) It confirms only that the program produces the expected outcome for the input 92; it provides no evidence about any other input. [2]

(b) A single passing case cannot prove the program is correct for all inputs: the program may still have a logic error that appears only for other values — for example, inputs at the extremes (0 or 100) or just beyond them. Passing tests are evidence, not proof, of correctness. [2]

Learning Objective [CRD-2.N] — Use “commenting out” lines of code as a debugging strategy.

使用"注释掉（commenting out）"代码行作为调试（debugging）策略。核心概念：注释掉某行可临时禁用该行而不从文件中删除；逐个注释可疑代码行可隔离导致错误行为的代码段；这是在 CRD-2.I.5 五种方法之外新增的第六种有效查错方法。

  • [CRD-2.N.1]: Commenting out a line of code temporarily disables it — the program ignores it during execution — without deleting it from the file.
  • [CRD-2.N.2]: By commenting out suspected lines one at a time, a programmer can isolate which code segment causes the incorrect behavior.
  • [CRD-2.N.3]: This is the sixth effective way to find and correct errors (added in the Quiz 1 rubric), extending the five ways listed in CRD-2.I.5: test cases; hand tracing; visualizations; debuggers; adding extra output statements; commenting out lines of code.
✏️ Exercise 1.4.7 — Commenting Out Lines of Code (4 marks)

(a) What does it mean to “comment out” a line of code, and how is it different from deleting it? [2]

(b) A program outputs an incorrect total. Describe how a programmer could use commenting out to find the error. [2]

📖 参考答案 | Reference Answer

(a) Commenting out a line turns it into a comment, so the program ignores it during execution, but the line remains in the file and can easily be restored. Deleting removes the line permanently. [2]

(b) The programmer comments out lines one at a time (or in small groups), running the program after each change and checking whether the total becomes correct; the line whose removal fixes the output is the one causing the error. [2]
