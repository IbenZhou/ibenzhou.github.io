Processors, Parallel Processing and Virtual Machines

This section covers the five A2 exam points of §15.1: RISC and CISC processor designs (including interrupt handling), pipelining and registers in RISC, the four basic computer architectures, massively parallel computers, and the concept of a virtual machine.

RISC and CISC processors

Instruction sets

  • A computer processor has an instruction set — the complete collection of machine-code instructions it can recognise and execute.
  • The instruction set varies from one processor to another, and different design philosophies make different trade-offs between instruction complexity, clock cycles per instruction and hardware simplicity.
  • There are two contrasting designs:
    • Reduced Instruction Set Computer (RISC)
    • Complex Instruction Set Computer (CISC)

RISC

  • Reduced Instruction Set Computer (RISC) uses a smaller instruction set built from simple instructions.
  • Each instruction generally takes one clock cycle to execute, which makes RISC well suited to pipelining.
  • Uses fixed-length / fixed-format instructions and few addressing modes, so decoding is simple.
  • Uses many general-purpose registers and relies heavily on software / the compiler (design emphasis is on the software).
  • Uses a hard-wired control unit and relatively few transistors.
  • A RISC program may require more instructions, because each instruction performs a simpler operation.
  • Typically used in smartphones and tablets.

CISC

  • Complex Instruction Set Computer (CISC) uses a larger instruction set, including complex, multi-operation instructions.
  • Instructions are variable length and may take more than one clock cycle to execute; decoding is complex and uses microcode / a programmable control unit.
  • Uses many addressing modes but fewer general-purpose registers.
  • Instructions take up less space in memory (fewer instructions are needed).
  • Design emphasis is on the hardware; makes frequent use of cache memory.
  • Typically used in laptops and desktop computers.

  • A program written for a RISC processor will not run directly on a CISC processor, and vice versa, because the instruction sets differ.
  • A program written for one RISC processor may not necessarily run on another RISC processor if their instruction sets differ.

Interrupt handling on RISC and CISC

  • The general concept of interrupts is covered in Chapter04-Interrupt.
  • Both architectures support interrupts and aim to respond quickly and resume execution correctly; they differ in how much of the work is done in hardware.
Feature CISC RISC
Instruction complexity Complex instructions, often with built-in support for interrupt routines Simple, fixed-length instructions; interrupt handling done with simpler routines

Interrupt handling ★

The process that can be applied to either architecture:

  • The processor detects an interrupt at the start or end of the fetch-execute cycle (raised by hardware, a timer or software).
  • The current program is temporarily stopped and the status of each register is stored on the stack (context is saved); the interrupt vector identifies the correct ISR.
  • The Interrupt Service Routine (ISR) is executed.
  • Afterwards the registers are restored to their original status from the stack and the interrupted program resumes at the correct point.
  • With pipelining, several instructions may still be in the pipeline when the interrupt arrives; this adds complexity. Instructions currently in operation are usually discarded except for the one at write back, the handler is applied to the remaining instruction, and the processor restarts with the next instruction in sequence once the interrupt has been serviced.

Pipelining and registers in RISC processors

What is pipelining?

  • Pipelining is the process of carrying out several instructions concurrently, with each instruction at a different stage of the fetch-execute cycle.
  • One instruction can be fetched while the previous one is being decoded and the one before is being executed — this raises the number of instructions completed per unit time (throughput).
  • Each stage / subtask is completed during one clock cycle, and no two instructions execute the same stage at the same clock cycle.
  • On a branch, the pipeline may need to be flushed.
Fetch Decode Execute
Step 1 Instruction A
Step 2 Instruction B Instruction A
Step 3 Instruction C Instruction B Instruction A
Step 4 Instruction D Instruction C Instruction B

The five pipeline stages ★

  • Instruction fetch (IF) → instruction decode (ID) → operand fetch (OF) → instruction execute (IE) → write back result (WB).
  • Each stage is carried out using a different register when pipelining is used, so a partially processed instruction can be handed from one stage to the next.
  • The first instruction completes after five clock cycles; with six instructions, the last completes after ten cycles (no extra cycles per row).

Pipelining and registers in RISC ★

  • RISC processors are designed for pipelining efficiency: one clock cycle per instruction, fixed-length instructions and a limited instruction set keep every stage short and uniform.
  • A large general-purpose register file lets operands be held inside the CPU instead of repeatedly accessing RAM, reducing memory bottlenecks and avoiding stall cycles that would break the pipeline.
  • Intermediate values are stored in registers between stages — e.g. instruction A loads a value into R1, instruction B computes R1 + R2 into R3, all within the CPU.

Pipelining hazards ★

  • Structural hazard — two instructions need the same hardware resource in the same clock cycle (e.g. one memory used for both instruction fetch and operand fetch); removed by duplicating the resource (separate instruction and data caches) or by stalling.
  • Data hazard — an instruction needs an operand that an earlier instruction has not yet written back; removed by forwarding, inserting a stall, or compiler re-ordering of independent instructions.
  • Control hazard — a branch means the next address is unknown until the branch resolves; the pipeline is flushed and re-fetched, or branch prediction is used to keep it full.

Benefits of pipelining

Advantage Explanation
Increased throughput Multiple instructions handled at once
Better use of CPU components Fetch, decode and execute units are all in use simultaneously
Reduced idle time No waiting between stages
Faster execution of an instruction stream Even if individual instructions do not run faster

The four basic computer architectures

Flynn's classification

  • A computer architecture is the design and structure of a system — how it fetches, processes and stores data and instructions, and how CPU, memory and I/O work together.
  • Flynn’s taxonomy classifies architectures by how many instruction streams and data streams they support:
    • Single or Multiple Instruction stream
    • Single or Multiple Data stream

SISD — Single Instruction, Single Data

  • One processor executes one instruction on one data stream at a time.
  • Data comes from a single source and one instruction is performed on it.
  • Contains one processor, a control unit and a memory unit, executing instructions sequentially.
  • Traditional serial (non-parallel) architecture; used in basic single-core processors.

SIMD — Single Instruction, Multiple Data

  • One instruction is applied to many different data streams / elements simultaneously (e.g. array processors).
  • The instructions may be performed sequentially, taking advantage of pipelining.
  • Parallel computers with multiple processors, all performing the same operation in parallel.
  • Ideal for graphics, image processing and scientific computation (e.g. GPUs).

MISD — Multiple Instruction, Single Data

  • Multiple processors execute different operations on the same data stream.
  • Each processor works on the same data stream independently.
  • Very uncommon in practice; used in specialised fault-tolerant systems where each unit checks the same input differently.

MIMD — Multiple Instruction, Multiple Data

  • Multiple processors execute different instructions on different sets of data; any processor can do so at any time.
  • Processors operate asynchronously / independently, allowing full concurrent processing of separate tasks.
  • Most modern multi-core processors, distributed systems and cloud computing use this model; flexible and scalable.

Summary table

Architecture Instruction stream Data stream Used in
SISD Single Single Standard sequential / single-core processors
SIMD Single Multiple Vector processing (e.g. GPUs), array processors
MISD Multiple Single Specialised fault-tolerant systems
MIMD Multiple Multiple Multi-core processors, parallel / distributed systems

Massively parallel computers

What are massively parallel computers?

  • Massively parallel computers link many (thousands of) processors / computers together to form a more powerful single machine.
  • All the processors work simultaneously on the same large problem, each responsible for its own part of the problem; the partial results are combined to give the final output.
  • They tackle complex, large-scale tasks that can be decomposed into parallel work, e.g. scientific research, weather simulation, cryptography and AI.

Key characteristics

Feature Description
Many processors Thousands of processors are linked and work together on different parts of the same task
Single machine They form a more powerful ‘single machine’
Simultaneous operation All processors work simultaneously with coordinated / collaborative processing
Interconnects Communication via interconnected data pathways / networks, or via shared pools of memory
Message passing Processors communicate through a message interface / by sending messages
Shared or distributed memory Each processor may have its own memory or access shared memory resources
Specialised software Work must be distributed efficiently across the processors

Massively parallel vs cluster computers

Massively parallel computers Cluster computers
Thousands of processors form a single tightly integrated system Multiple independent systems networked together
Processors communicate continuously via shared architecture Communication via a network, often loosely coupled
Acts like one machine with distributed processing A group of co-operating systems
Higher performance, used for supercomputing tasks More general-purpose or batch processing systems

Link to computer architectures

  • Massively parallel systems often use SIMD (one instruction applied to many data points) or MIMD (different instructions on different data, fully independently).

Virtual machines

What is a virtual machine?

  • A virtual machine (VM) is a standalone environment running on a physical computer — it is not itself a physical machine.
  • It emulates the hardware / software of another system: the VM software has all the components of a physical computer system, while the host machine provides the physical resources (RAM, ROM, processor, storage) and is controlled by a host operating system.
  • This lets a user run software designed for a different operating system (e.g. Windows running a macOS VM), navigate its GUI and install software inside it.
  • VM management software runs a hypervisor, which monitors all activity inside the VM.

Host, guest and hypervisor ★

  • Host operating system — installed directly on the physical machine; controls all its physical resources, runs the virtual machine software and provides the user interface to operate it.
  • Guest operating system — installed inside the VM; runs under the control of the host, controls/accesses the virtual hardware, and reaches real devices only through the VM and host OS.
  • Hypervisor (virtual machine monitor) — sits between host and guest; creates and runs VMs, allocates host resources to each guest and traps privileged instructions so a guest cannot damage the host.

System VM versus process VM ★

  • A system VM runs a complete operating system on virtual hardware (e.g. VMware / VirtualBox running a full OS, or a cloud instance).
  • A process VM runs a single program on top of the host OS — e.g. the JVM executing Java bytecode.

Cross-platform and forwards compatibility

  • Not all software runs on all operating systems (e.g. some macOS software is performance-locked to macOS); a VM of the required OS lets a user run it.
  • Some software needs updating for the latest OS; a VM of an earlier release can run an application that has not received a forwards-compatibility update.

Benefits and limitations of VMs ★

Benefits (examples from the mark schemes):

  • Compatibility — run applications / legacy software incompatible with the host; emulate old software; emulate a different instruction set architecture; try software on different OS on the same hardware; multiple OS environments on one computer.
  • Protection — the guest has no effect on the host or other VMs; a guest can crash without crashing the host; suspicious software only infects the VM.
  • Cost — no need to buy extra hardware, since multiple VMs run on the same machine.

Limitations:

  • Performance — the guest is less efficient than a real machine because hardware is accessed indirectly through the host; response times cannot be measured accurately; multiple VMs compete for host resources.
  • Dependence on the host — the VM is limited by the host’s features/weaknesses and not all hardware/software can be emulated.
  • Complexity — building and maintaining a VM in-house is expensive, time-consuming and specialised.

VMs in software testing

  • VMs create isolated test environments that leave the host unaffected: developers can monitor performance impact, test on a clean-slate system and test against various OS (macOS, Linux, Windows).
  • VM software can emulate older hardware, so developers can build software that works on older machines and reach more users.

Consequences of running VMs

  • VMs share the host’s hardware; over-use can exhaust CPU, disk space and memory. VM software (e.g. VirtualBox) can cap resources — e.g. 1 GB RAM and 20% CPU on a low-spec machine, up to 8 GB RAM and 50% CPU on a high-spec machine.
